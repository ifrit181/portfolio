# <a id="sql-и-api-для-системного-аналитика-структурированная-карта-компетенций">SQL и API для системного аналитика: структурированная карта компетенций</a>

## <a id="1-общая-логика-зачем-аналитику-sql-и-api">1. Общая логика: зачем аналитику SQL и API</a>

| Область | Роль в работе аналитика | Что даёт |
|---|---|---|
| **SQL** | Проверка данных, анализ edge cases, описание требований к хранению | Понимание, откуда берутся данные и как их проверить |
| **API** | Проектирование интеграций, описание контрактов, сценариев обмена | Понимание, как системы взаимодействуют и какие данные передают |
| **Связка SQL + API** | Проектирование фичи от источника до хранения и отображения | Целостная картина: запрос → API → БД → отчёт/интерфейс |

## <a id="2-sql-структура-знаний">2. SQL: структура знаний</a>

### <a id="2-1-уровни-владения">2.1. Уровни владения</a>

| Уровень | Что уметь | Для чего |
|---|---|---|
| **Базовый** | SELECT, WHERE, ORDER BY, LIMIT | Посмотреть данные, отфильтровать, отсортировать |
| **Рабочий** | JOIN, GROUP BY, HAVING, агрегаты, подзапросы | Считать метрики, проверять связи, находить аномалии |
| **Продвинутый** | CTE, оконные функции, UNION, сложные подзапросы | Анализ трендов, сложные проверки, подготовка отчётов |

### <a id="2-2-ключевые-темы">2.2. Ключевые темы</a>

| Раздел | Что знать | Пример | Зачем аналитику |
|---|---|---|---|
| **SELECT** | Выборка полей, псевдонимы, DISTINCT | `SELECT name, email FROM users;` | Быстрый просмотр данных |
| **WHERE** | Фильтрация, операторы `=`, `IN`, `BETWEEN`, `LIKE`, `IS NULL` | `WHERE status = 'active'` | Проверка условий |
| **JOIN** | INNER, LEFT, RIGHT, FULL | `LEFT JOIN orders ON users.id = orders.user_id` | Связь таблиц, поиск пропусков |
| **GROUP BY** | Агрегация: COUNT, SUM, AVG, MIN, MAX | `GROUP BY user_id` | Метрики, отчёты |
| **HAVING** | Фильтр после группировки | `HAVING SUM(amount) > 1000` | Отбор групп |
| **Подзапросы** | В WHERE, FROM, SELECT | `WHERE id IN (SELECT user_id FROM orders)` | Сложные условия |
| **CTE (WITH)** | Временные именованные наборы | `WITH active AS (...) SELECT ...` | Читаемость сложных запросов |
| **Оконные функции** | ROW_NUMBER, RANK, SUM OVER | `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY date)` | Аналитика, дедупликация |
| **Структура БД** | PK, FK, типы данных, ER-диаграммы | `users.id → orders.user_id` | Проектирование требований к данным |

### <a id="2-3-пример-рабочего-запроса">2.3. Пример рабочего запроса</a>

```sql
WITH user_orders AS (
  SELECT user_id, COUNT(*) AS cnt, SUM(total) AS revenue
  FROM orders
  WHERE created_at >= '2026-01-01'
  GROUP BY user_id
)
SELECT u.name, uo.cnt, uo.revenue
FROM users u
LEFT JOIN user_orders uo ON u.id = uo.user_id
ORDER BY uo.revenue DESC NULLS LAST;
```

## <a id="3-api-структура-знаний">3. API: структура знаний</a>

### <a id="3-1-типы-api">3.1. Типы API</a>

| Тип | Особенности | Где встречается |
|---|---|---|
| **REST** | HTTP-методы, JSON, ресурсы | Большинство современных сервисов |
| **SOAP** | XML, строгий контракт | Legacy, enterprise, банки |
| **GraphQL** | Клиент сам выбирает поля | Гибкие фронтенды |
| **WebSocket** | Двусторонний real-time | Чаты, уведомления, трейдинг |

### <a id="3-2-rest-основные-понятия">3.2. REST: основные понятия</a>

| Элемент | Что знать | Пример |
|---|---|---|
| **Ресурс** | URL-сущность | `/users`, `/orders/123` |
| **HTTP-методы** | GET, POST, PUT, PATCH, DELETE | `POST /orders` — создать заказ |
| **Статус-коды** | 200, 201, 400, 401, 403, 404, 500 | `404` — не найдено |
| **Query params** | Фильтры, пагинация | `?page=1&limit=20` |
| **Headers** | Тип данных, авторизация | `Content-Type: application/json` |
| **Body** | Тело запроса/ответа | JSON с полями |
| **Path params** | Параметры в URL | `/users/{id}` |

### <a id="3-3-аутентификация-и-авторизация">3.3. Аутентификация и авторизация</a>

| Способ | Что это | Что описывает аналитик |
|---|---|---|
| **API-ключ** | Простой ключ в заголовке | `X-API-Key: ...` |
| **OAuth 2.0** | Токен доступа | `Authorization: Bearer <token>` |
| **JWT** | Токен с данными пользователя | Срок жизни, claims |

### <a id="3-4-документирование-api">3.4. Документирование API</a>

- **OpenAPI / Swagger** — стандарт описания контрактов.
- **Postman** — тестирование и коллекции запросов.

Пример фрагмента OpenAPI:

```yaml
/users/{id}:
  get:
    summary: Получить пользователя
    parameters:
      - name: id
        in: path
        required: true
        schema:
          type: integer
    responses:
      '200':
        description: Успех
      '404':
        description: Не найден
```

### <a id="3-5-что-делает-аналитик-с-api">3.5. Что делает аналитик с API</a>

| Задача | Результат |
|---|---|
| Проектирование контракта | Спецификация endpoint’ов, полей, ошибок |
| Описание интеграции | Сценарии: кто, когда, что передаёт |
| Маппинг данных | Соответствие полей между системами |
| Обработка ошибок | Что делать при 400, 401, 500, таймауте |
| Тестирование | Проверка через Postman/Swagger |

### <a id="3-6-интеграционные-паттерны">3.6. Интеграционные паттерны</a>

| Паттерн | Когда использовать |
|---|---|
| **Синхронный** | Запрос-ответ, нужен немедленный результат |
| **Асинхронный** | Очереди (Kafka, RabbitMQ), webhooks |
| **Пакетный** | Выгрузка CSV/XML, ночная синхронизация |

### <a id="4-2-пример-проектирование-фичи-синхронизация-заказов">4.2. Пример: проектирование фичи «Синхронизация заказов»</a>

## <a id="5-рекомендуемый-порядок-изучения">5. Рекомендуемый порядок изучения</a>

1. **SQL:** SELECT, WHERE, ORDER BY, LIMIT.
2. **SQL:** JOIN, GROUP BY, HAVING, агрегаты.
3. **SQL:** подзапросы, CTE, оконные функции.
4. **API:** REST, HTTP-методы, статус-коды, JSON.
5. **API:** Postman, чтение Swagger.
6. **API:** проектирование endpoint’ов, OpenAPI.
7. **Интеграции:** синхронные/асинхронные, webhooks, очереди.
8. **Практика:** сквозной кейс — от требования до SQL-проверки и API-контракта.

## <a id="6-частые-ошибки">6. Частые ошибки</a>

| Ошибка | Как избежать |
|---|---|
| Игнорировать NULL в SQL | Проверять `IS NULL`, `COALESCE` |
| Забыть про LEFT JOIN | Проверять, не теряются ли данные |
| Не описывать ошибки API | Всегда указывать 400, 401, 404, 500 |
| Не проверять маппинг полей | Составлять таблицу соответствия |
| Путать PUT и PATCH | PUT — полная замена, PATCH — частичная |
| Не учитывать таймауты | Описывать retry и fallback |
