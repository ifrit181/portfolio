## <a id="1-зачем-аналитику-очереди">1. Зачем аналитику очереди</a>

Когда интеграция асинхронная, аналитик должен понимать:
- какой брокер используется;
- какие топики / очереди;
- формат сообщений;
- гарантии доставки.

Без этого спецификация интеграции будет неполной.

---

## <a id="2-что-такое-очередь">2. Что такое очередь</a>

**Очередь** — буфер между producer (отправитель) и consumer (получатель).

```
Producer → [Очередь] → Consumer
```

**Зачем:**
- развязка по времени (сервис-получатель может быть недоступен);
- сглаживание пиков (буфер);
- гарантированная доставка (сообщение не потеряется);
- масштабирование (несколько consumer'ов).

---

## <a id="3-синхронно-vs-асинхронно">3. Синхронно vs асинхронно</a>

| | Синхронно (HTTP) | Асинхронно (очередь) |
|---|---|---|
| Ответ | Сразу | Позже |
| Связность | Сильная | Слабая |
| Устойчивость | Ломается при сбое | Устойчиво |
| Сложность | Низкая | Высокая |
| Когда | Нужен immediate результат | Обработка, рассылки |

**Комбинированный паттерн:** HTTP-запрос → постановка в очередь → ответ `202 Accepted` + `job_id`. Клиент опрашивает статус.

## 4. Kafka

**Kafka** — распределённый лог событий.

### <a id="основные-понятия">Основные понятия</a>

| Термин | Значение |
|---|---|
| Topic | Категория сообщений |
| Partition | Часть топика (для параллелизма) |
| Offset | Позиция сообщения в партиции |
| Producer | Пишет в топик |
| Consumer | Читает из топика |
| Consumer Group | Группа consumer'ов |
| Key | Ключ партиционирования |

### <a id="особенности">Особенности</a>

- Хранит сообщения долго (дни, недели).
- Можно перечитать с любого offset.
- Ordering гарантирован внутри партиции.
- Не удаляет сообщение после прочтения.

### <a id="где-использовать">Где использовать</a>

- Event sourcing;
- Потоковая аналитика;
- Логирование;
- CDC (Change Data Capture).

### <a id="что-описывает-аналитик">Что описывает аналитик</a>

- Имя топика (`orders.created`).
- Формат сообщения (JSON, Avro).
- Ключ партиционирования (`order_id`).
- Retention (сколько хранить).
- Consumer group.

**Пример:**
```json
{
  "event_id": "evt_123",
  "event_type": "order.created",
  "timestamp": "2026-10-14T10:30:00Z",
  "data": { "order_id": 456, "user_id": 123 }
}
```

## 5. RabbitMQ

**RabbitMQ** — классический брокер сообщений.

### <a id="основные-понятия-2">Основные понятия</a>

| Термин | Значение |
|---|---|
| Exchange | Точка приёма |
| Queue | Очередь |
| Binding | Правило маршрутизации |
| Routing Key | Ключ маршрутизации |
| Consumer | Читает из очереди |

### <a id="типы-exchange">Типы exchange</a>

| Тип | Как маршрутизирует |
|---|---|
| `direct` | По точному routing key |
| `fanout` | Во все очереди |
| `topic` | По шаблону (`orders.*`) |
| `headers` | По заголовкам |

### <a id="особенности-2">Особенности</a>

- Сообщение удаляется после подтверждения (ack).
- TTL у очереди.
- Приоритеты.
- DLQ.

### <a id="где-использовать-2">Где использовать</a>

- Task queues;
- RPC;
- Микросервисы.

## 6. AWS SQS / SNS

| | SQS | SNS |
|---|---|---|
| Модель | Очередь | Pub/Sub |
| Получатель | Один | Много |
| Хранение | До 14 дней | Не хранит |
| Гарантия | at-least-once | at-least-once |
| Ordering | FIFO (опционально) | Нет |

**Комбинация:** SNS → SQS (fanout на несколько очередей).

**Где использовать:** serverless, AWS-инфраструктура.

---

## <a id="7-гарантии-доставки">7. Гарантии доставки</a>

| Гарантия | Что означает | Где |
|---|---|---|
| At-most-once | Может потеряться | Редко |
| At-least-once | Не потеряется, но может задвоиться | Kafka, RabbitMQ, SQS |
| Exactly-once | Ровно один раз | Kafka (транзакции) |

**Практика:** at-least-once + идемпотентность на consumer.

## <a id="8-паттерны">8. Паттерны</a>

### Point-to-Point

Одно сообщение → один consumer.

```
Producer → Queue → Consumer
```

### <a id="pub-sub">Pub/Sub</a>

Одно сообщение → много подписчиков.

```
Producer → Topic → [Consumer A, Consumer B, Consumer C]
```

### Competing Consumers

Несколько consumer'ов одной группы читают из одной очереди.

```
Producer → Queue → [Consumer 1, Consumer 2, Consumer 3]
```

### Dead Letter Queue

Сообщения, не обработанные после N попыток, идут в DLQ.

### Saga

Распределённая транзакция через последовательность событий.

### Outbox

Запись в БД + публикация события атомарно:
1. Транзакция: `INSERT INTO orders` + `INSERT INTO outbox`.
2. Отдельный процесс читает outbox и публикует в Kafka.
3. Помечает как отправленные.

**Зачем:** избежать рассинхрона «БД записана, событие не отправлено».

## <a id="10-практика">10. Практика</a>

### <a id="задача-1">Задача 1</a>
Опишите поток «заказ создан».

**Producer:** Orders Service.
**Broker:** Kafka.
**Topic:** `orders.created`.
**Key:** `order_id` (гарантирует порядок для одного заказа).
**Формат:**
```json
{
  "event_id": "evt_123",
  "event_type": "order.created",
  "timestamp": "2026-10-14T10:30:00Z",
  "data": {
    "order_id": 456,
    "user_id": 123,
    "total": 1990.00
  }
}
```

**Consumers:**
- Analytics Service (читает для отчётов);
- 1С Sync (читает для синхронизации);
- Email Service (отправляет письмо).

**Retention:** 7 дней.
**Гарантия:** at-least-once.
**Consumer идемпотентен по `event_id`.**

### <a id="задача-2">Задача 2</a>
Опишите Outbox-паттерн для заказов.

```sql
BEGIN;
INSERT INTO orders (...) VALUES (...);
INSERT INTO outbox (event_type, payload) VALUES ('order.created', '{"order_id": 456}');
COMMIT;
```

Отдельный publisher читает `outbox` → публикует в Kafka → помечает `published_at`.

### <a id="задача-3">Задача 3</a>
Опишите DLQ-политику.

| Параметр | Значение |
|---|---|
| Max attempts | 5 |
| Backoff | 1s → 5s → 30s → 5m → 30m |
| DLQ топик | `orders.dlq` |
| Разбор | Ручной, алерт дежурному |
| Переотправка | Через админский endpoint |
