## 1. Зачем аналитику webhooks

Webhooks — основной способ «push»-уведомлений в современных API. Аналитик описывает:
- какие события бывают;
- что в payload;
- как проверять подпись;
- что делать при неудаче.

---

## 2. Что такое webhook

**Webhook** — HTTP-запрос, который одна система отправляет другой при наступлении события.

```
1. Клиент регистрирует URL: POST /api/v1/webhooks { "url": "https://client.com/hooks" }
2. В системе происходит событие (order.paid)
3. Система отправляет POST на URL клиента
4. Клиент отвечает 2xx
```

**В отличие от polling:**
- не нужно опрашивать сервер;
- событие доходит почти сразу;
- меньше нагрузки.

---

## 3. События и подписки

### Регистрация

```http
POST /api/v1/webhooks
{
  "url": "https://client.com/hooks",
  "events": ["order.paid", "order.shipped", "order.cancelled"],
  "secret": "shared-secret-for-hmac"
}
```

### Список событий

| Событие | Когда |
|---|---|
| `order.created` | Заказ создан |
| `order.paid` | Оплачен |
| `order.shipped` | Отправлен |
| `order.cancelled` | Отменён |
| `payment.failed` | Платёж не прошёл |
| `user.registered` | Регистрация |
| `user.deleted` | Удаление |

**Аналитик описывает:** полный список событий, их триггеры, поля.

## 4. Формат payload

```json
{
  "id": "evt_123",
  "event": "order.paid",
  "timestamp": "2026-10-14T10:30:00Z",
  "api_version": "v1",
  "data": {
    "order_id": 456,
    "user_id": 123,
    "amount": 1990.00,
    "currency": "RUB"
  }
}
```

| Поле | Зачем |
|---|---|
| `id` | Уникальный ID события (для идемпотентности) |
| `event` | Тип события |
| `timestamp` | Когда произошло |
| `api_version` | Версия контракта |
| `data` | Данные события |

**Что важно:** payload минимальный — только то, что нужно клиенту. Клиент может дочитать через API.

## 5. Безопасность

### Подпись HMAC

1. Сервер и клиент делят общий секрет.
2. Сервер считает HMAC-SHA256 от тела.
3. Отправляет подпись в заголовке.

```http
POST /hooks
X-Signature: sha256=5f4dcc3b5aa765d61d8327deb882cf99...
X-Timestamp: 1737000000
```

**Проверка клиентом:**
```
expected = HMAC_SHA256(secret, timestamp + body)
compare(expected, signature)
```

### Защита от replay

- Таймстамп в заголовке.
- Клиент отклоняет события старше N минут.
- Опционально — nonce.

### HTTPS

Только HTTPS. HTTP-эндпоинты не принимаются.

### Список IP

Иногда сервер публикует список IP, с которых идут webhooks — клиент может фильтровать.

## 6. Retry и доставка

### Что считается успехом

**2xx** — успех.
**4xx** — ошибка клиента, не повторяем (кроме 408, 429).
**5xx / timeout** — повторяем.

### Политика retry (типичная)

| Попытка | Задержка |
|---|---|
| 1 | сразу |
| 2 | 1 мин |
| 3 | 5 мин |
| 4 | 30 мин |
| 5 | 2 часа |
| 6 | 6 часов |
| 7 | 24 часа |

### Таймаут

Обычно 5–30 секунд. Если дольше — считать ошибкой.

### Отключение

После N неудачных попыток webhook может быть отключён. Клиент получает уведомление на email.

## 7. Идемпотентность

Webhooks могут приходить дважды. Клиент должен уметь:
- хранить `event_id`;
- игнорировать повторные доставки.

**В ТЗ:** явно указать, что доставка at-least-once, обработчик должен быть идемпотентным.

---

## 8. Порядок доставки

**Гарантий порядка нет.** Событие `order.shipped` может прийти раньше `order.paid`.

**Что делать клиенту:**
- проверять `timestamp`;
- использовать state machine;
- игнорировать «устаревшие» события.

**В ТЗ:** явно указать, что порядок не гарантирован.

---

## 9. Мониторинг

Что должен видеть клиент:
- история доставок (успех / ошибка / код ответа);
- количество неудач;
- возможность переотправить.

Что должен видеть отправитель:
- success rate по webhook'ам;
- алерты при массовых ошибках;
- автоматическое отключение проблемных URL.

## 10. Практика

### Задача 1
Опишите webhook для `order.paid`.

**Payload:**
```json
{
  "id": "evt_123",
  "event": "order.paid",
  "timestamp": "2026-10-14T10:30:00Z",
  "api_version": "v1",
  "data": {
    "order_id": 456,
    "amount": 1990.00,
    "currency": "RUB",
    "paid_at": "2026-10-14T10:30:00Z"
  }
}
```

**Заголовки:**
```http
Content-Type: application/json
X-Signature: sha256=...
X-Timestamp: 1737000000
X-Event-Id: evt_123
X-Event-Type: order.paid
```

**Ожидаемый ответ клиента:**
```http
HTTP/1.1 200 OK
```

**Retry:** 7 попыток с экспоненциальной задержкой.
**Идемпотентность:** по `X-Event-Id`.
**Порядок:** не гарантируется.

### Задача 2
Опишите сценарий обработки webhook у клиента.

1. Получен `POST /hooks` с `X-Signature`.
2. Проверить HMAC от `timestamp + body`.
3. Проверить `timestamp` (не старше 5 минут).
4. Проверить `X-Event-Id` в БД:
   - если есть — вернуть `200` и не обрабатывать;
   - если нет — обработать, сохранить ID, вернуть `200`.
5. Если обработка упала — вернуть `500`, чтобы сервер повторил.

### Задача 3
Опишите мониторинг webhooks.

| Метрика | Алерт |
|---|---|
| Success rate < 95% за 15 мин | Warning |
| Success rate < 80% за 15 мин | Critical |
| Webhook отключён после N ошибок | Info клиенту |
| Задержка доставки > 1 мин | Warning |
