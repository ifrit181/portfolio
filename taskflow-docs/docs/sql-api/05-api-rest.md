## <a id="1-что-такое-api">1. Что такое API</a>

**API (Application Programming Interface)** — контракт, по которому одна
система обращается к другой. Это набор правил: если отправить такой запрос,
придёт такой ответ.

**Примеры:**

- Мобильное приложение → сервер (получить список заказов пользователя).
- Интернет-магазин → платёжный шлюз (провести оплату).
- CRM → 1С (синхронизировать клиентов).

**Что делает аналитик:**

- проектирует, какие endpoint'ы нужны;
- описывает, какие поля передаются в запросе и ответе;
- определяет, что происходит при ошибках;
- согласовывает контракт с разработчиками и бизнесом.

📖 Подробнее о работе аналитика с API — в
[08-api-integrations.md](08-api-integrations.md).

## <a id="2-rest-принципы">2. REST: принципы</a>

**REST (Representational State Transfer)** — архитектурный стиль. Это не
протокол и не стандарт, а набор рекомендаций, как проектировать
взаимодействие между системами.

### <a id="ключевые-принципы">Ключевые принципы</a>

**1. Клиент-сервер.** Клиент (браузер, приложение) и сервер — раздельные
системы. Клиент не знает, как устроен сервер; сервер не знает, что за клиент.
Это позволяет менять одну сторону, не затрагивая другую.

**2. Stateless (без состояния).** Каждый запрос независим — сервер не хранит
информацию о предыдущих запросах клиента. Всё нужное для обработки запроса
передаётся в самом запросе: токен, параметры, тело.

*Почему это важно:* если сервер хранит состояние, при перезапуске оно
потеряется. А ещё придётся «привязывать» клиента к конкретному серверу — это
плохо масштабируется.

**3. Кэшируемость.** Ответы можно кэшировать. Если данные не меняются —
клиент или промежуточный прокси не запрашивает их заново. Это снижает нагрузку
и ускоряет работу.

**4. Единый интерфейс.** Все ресурсы называются одинаково, используют
стандартные HTTP-методы и статус-коды. Клиент, зная правила, может работать
с любым REST API без документации.

**5. Слои.** Между клиентом и сервером могут быть прокси, балансировщики,
CDN — клиент об этом не знает и не должен знать.

## <a id="3-ресурсы-и-url">3. Ресурсы и URL</a>

**Ресурс** — это сущность, с которой работает API: пользователь, заказ,
товар, платёж. Ресурс идентифицируется через URL.

| Действие | URL | Метод |
|---|---|---|
| Список пользователей | `/users` | GET |
| Один пользователь | `/users/123` | GET |
| Создать пользователя | `/users` | POST |
| Обновить | `/users/123` | PUT/PATCH |
| Удалить | `/users/123` | DELETE |
| Заказы пользователя | `/users/123/orders` | GET |

### <a id="правила-именования">Правила именования</a>

- **Существительные во множественном числе:** `/users`, а не `/getUsers`.
  Действие определяется методом (`GET /users`), а не глаголом в URL.
- **Вложенность для связей:** `/users/123/orders` — заказы пользователя 123.
  Не более 2 уровней вложенности.
- **Lowercase, дефисы:** `/order-items`, а не `/OrderItems` или `/order_items`.
- **Без расширений:** `/products`, а не `/products.json`.

📖 Подробнее о паттернах именования и пагинации — в
[16-api-design-patterns.md](16-api-design-patterns.md).

## <a id="4-http-методы">4. HTTP-методы</a>

HTTP-методы определяют, какое действие выполняется над ресурсом.

| Метод | Назначение | Идемпотентный | Безопасный |
|---|---|---|---|
| `GET` | Получить | ✅ | ✅ |
| `POST` | Создать | ❌ | ❌ |
| `PUT` | Полностью заменить | ✅ | ❌ |
| `PATCH` | Частично обновить | ❌* | ❌ |
| `DELETE` | Удалить | ✅ | ❌ |

### <a id="что-такое-идемпотентность">Что такое идемпотентность</a>

**Идемпотентность** — свойство операции: повторный вызов даёт **тот же
результат**, что и первый. Не важно, вызвали вы метод один раз или пять —
состояние системы не изменится.

**Примеры:**

- `GET /orders/1` — сколько ни вызывай, вернёт тот же заказ. ✅ Идемпотентен.
- `DELETE /orders/1` — первый вызов удалит, второй вернёт `404`, но состояние
  не изменится. ✅ Идемпотентен.
- `POST /orders` — каждый вызов создаёт новый заказ. ❌ Не идемпотентен.
- `PUT /users/123` — полная замена. ✅ Идемпотентен.
- `PATCH /users/123` — частичное обновление. ❌ Может быть неидемпотентным,
  если в теле есть операции вроде «увеличить счётчик на 1».

**Зачем это знать аналитику.** Если клиент не получил ответ из-за таймаута,
он может повторить запрос. Для идемпотентных методов это безопасно. Для
`POST` — риск создать дубль. Решение — `Idempotency-Key`.

📖 Подробнее об идемпотентности и retry — в
[17-api-idempotency.md](17-api-idempotency.md).

### <a id="что-такое-безопасность">Что такое безопасность</a>

**Безопасный метод** — тот, который **не меняет состояние** сервера. `GET`
безопасный: он только читает. `POST`, `PUT`, `PATCH`, `DELETE` — небезопасные,
потому что меняют данные.

### PUT vs PATCH

- **PUT** — заменяет объект целиком. Если в теле не указать поле — оно
  обнулится или сбросится к значению по умолчанию.
- **PATCH** — обновляет только переданные поля. Остальные сохраняются.

**Пример.** У пользователя `{name, email, phone}`. Хотим обновить email.

```http
PUT /users/123
{ "email": "new@example.com" }
```
→ `name` и `phone` обнулятся. ❌ Опасно.

```http
PATCH /users/123
{ "email": "new@example.com" }
```
→ Обновится только email. ✅ Правильно.

**Правило для ТЗ:** для частичного обновления всегда указывать `PATCH`.

## <a id="5-статус-коды">5. Статус-коды</a>

Статус-код — трёхзначное число в ответе сервера. Первая цифра говорит
о категории.

| Категория | Что означает |
|---|---|
| `2xx` | Успех |
| `3xx` | Редирект |
| `4xx` | Ошибка клиента (виноват запрос) |
| `5xx` | Ошибка сервера |

### <a id="успех-2xx">Успех (2xx)</a>

| Код | Значение | Когда использовать |
|---|---|---|
| `200 OK` | Успех | GET, PUT, PATCH |
| `201 Created` | Ресурс создан | POST |
| `202 Accepted` | Принято в обработку | Асинхронные операции |
| `204 No Content` | Успех без тела | DELETE |

### <a id="ошибка-клиента-4xx">Ошибка клиента (4xx)</a>

| Код | Значение | Когда использовать |
|---|---|---|
| `400 Bad Request` | Невалидные данные | Синтаксис запроса сломан |
| `401 Unauthorized` | Не аутентифицирован | Нет токена или истёк |
| `403 Forbidden` | Нет прав | Токен есть, но доступ запрещён |
| `404 Not Found` | Не найдено | Ресурс не существует |
| `405 Method Not Allowed` | Метод не поддерживается | DELETE на endpoint, где только GET |
| `409 Conflict` | Конфликт | Дубль по уникальному полю |
| `422 Unprocessable Entity` | Валидация не пройдена | Синтаксис верный, но данные нелогичны |
| `429 Too Many Requests` | Превышен лимит | Rate limiting |

**Разница 401 и 403:**

- `401` — «я не знаю, кто ты». Нужно аутентифицироваться.
- `403` — «я знаю, кто ты, но тебе нельзя». Аутентификация прошла,
  но прав нет.

### <a id="ошибка-сервера-5xx">Ошибка сервера (5xx)</a>

| Код | Значение |
|---|---|
| `500 Internal Server Error` | Общая ошибка сервера |
| `502 Bad Gateway` | Проблема с upstream-сервисом |
| `503 Service Unavailable` | Сервис недоступен (перегрузка, обслуживание) |
| `504 Gateway Timeout` | Upstream не ответил вовремя |

**Правило для ТЗ:** для каждого endpoint'а перечислить все возможные
статус-коды и что они означают.

📖 Полный разбор статус-кодов — в
[15-api-http-deep.md](15-api-http-deep.md) → раздел 5.

## <a id="6-структура-запроса">6. Структура запроса</a>

```
POST /api/v1/orders HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Accept: application/json

{
  "user_id": 123,
  "items": [
    { "product_id": 1, "quantity": 2 }
  ]
}
```

| Часть | Назначение | Пример |
|---|---|---|
| Request line | Метод + путь + версия HTTP | `POST /api/v1/orders HTTP/1.1` |
| `Host` | Куда обращаемся | `api.example.com` |
| `Content-Type` | Формат тела запроса | `application/json` |
| `Authorization` | Аутентификация | `Bearer <token>` |
| `Accept` | Ожидаемый формат ответа | `application/json` |
| Body | Данные | JSON с полями |

**Тело (body) есть только у POST, PUT, PATCH.** У GET и DELETE — нет.

## <a id="7-структура-ответа">7. Структура ответа</a>

### <a id="успех">Успех</a>

```json
{
  "id": 456,
  "user_id": 123,
  "status": "created",
  "total": 1990.00,
  "created_at": "2026-01-15T10:30:00Z"
}
```

### <a id="ошибка">Ошибка</a>

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "user_id is required",
    "details": [
      { "field": "user_id", "issue": "missing" }
    ]
  }
}
```

**Требования к описанию ошибок:**

- **стабильный код** (`VALIDATION_ERROR`) — для программной обработки;
- **человекочитаемое сообщение** — для логов и отображения;
- **детали** — что именно пошло не так.

**Почему код важнее текста.** Клиент не должен парсить текст — он может
меняться. Программа должна опираться на код: `if error.code == 'TOKEN_EXPIRED'`,
а не `if 'токен истёк' in error.message`.

📖 Формат ошибок и их коды — в
[16-api-design-patterns.md](16-api-design-patterns.md) → раздел 6.

## <a id="8-пагинация-фильтрация-сортировка">8. Пагинация, фильтрация, сортировка</a>

### <a id="пагинация">Пагинация</a>

Когда в БД много записей, отдавать их одним ответом нельзя — это долго
и тяжело. Нужно разбивать на страницы.

**Offset-based:**
```
GET /orders?page=2&limit=50
```
`page` — номер страницы, `limit` — сколько записей на странице.

**Проблема:** при вставке/удалении записи страницы «сдвигаются», и клиент
может пропустить или увидеть дубли.

**Cursor-based (надёжнее):**
```
GET /orders?cursor=eyJpZCI6MTIzfQ&limit=50
```
`cursor` — маркер последней записи. Следующий запрос начинается с неё.
Стабильно при изменениях.

📖 Подробнее — в [16-api-design-patterns.md](16-api-design-patterns.md) → раздел 3.

### <a id="фильтрация">Фильтрация</a>

```
GET /orders?status=paid&user_id=123&amount_gte=1000
```

`amount_gte` — «amount ≥ 1000». Такие суффиксы (`_gte`, `_lte`, `_gt`, `_lt`)
стандартны для фильтрации.

### <a id="сортировка">Сортировка</a>

```
GET /orders?sort=-created_at,amount
```

`-` перед полем — убывание. `,` — несколько полей. Здесь: сначала по дате
(убывание), потом по сумме (возрастание).

📖 Про версионирование и другие паттерны — в
[16-api-design-patterns.md](16-api-design-patterns.md).

## <a id="9-версионирование">9. Версионирование</a>

Когда API меняется несовместимо со старыми клиентами, нужно версионирование.
Старые клиенты продолжают работать со старой версией, новые — с новой.

| Способ | Пример | Плюсы | Минусы |
|---|---|---|---|
| В URL | `/api/v1/users` | Просто, видно в логах | URL «загрязняется» |
| В заголовке | `Accept: application/vnd.api.v1+json` | Чистый URL | Сложнее отлаживать |

**На практике чаще всего — в URL.** Это самый простой и наглядный способ.

**Breaking change** (несовместимое изменение):

- удалили поле из ответа;
- переименовали поле;
- изменили тип поля;
- сделали необязательное поле обязательным;
- изменили формат ошибки.

**Non-breaking change** (совместимое):

- добавили новое поле в ответ;
- добавили новый endpoint;
- добавили необязательный параметр.

📖 Подробнее — в [16-api-design-patterns.md](16-api-design-patterns.md) → раздел 8.

## <a id="10-практика">10. Практика</a>

### <a id="задача-1">Задача 1</a>
Опишите endpoint для получения списка заказов пользователя с фильтрами
и пагинацией.

**Запрос:**
```http
GET /api/v1/users/123/orders?status=paid&page=1&limit=20&sort=-created_at
Authorization: Bearer <token>
Accept: application/json
```

**Ответ 200:**
```json
{
  "data": [
    {
      "id": 456,
      "amount": 1990,
      "status": "paid",
      "created_at": "2026-01-15T10:30:00Z"
    }
  ],
  "pagination": {
    "page": 1,
    "limit": 20,
    "total": 137
  }
}
```

**Что важно в ответе:**

- коллекция обёрнута в поле `data` — так проще добавлять метаданные;
- есть блок `pagination` — клиент знает, что есть ещё страницы;
- дата в формате ISO 8601 (`2026-01-15T10:30:00Z`).

### <a id="задача-2">Задача 2</a>
Опишите сценарии ошибок для создания заказа.

| Код | Ситуация | Тело |
|---|---|---|
| 400 | Отсутствует `user_id` | `{"error": {"code": "VALIDATION_ERROR", "message": "user_id is required"}}` |
| 401 | Токен не передан | `{"error": {"code": "UNAUTHORIZED"}}` |
| 403 | Нет прав на создание | `{"error": {"code": "FORBIDDEN"}}` |
| 404 | `user_id` не найден | `{"error": {"code": "USER_NOT_FOUND"}}` |
| 409 | Дубль заказа | `{"error": {"code": "DUPLICATE_ORDER"}}` |
| 422 | `quantity` < 1 | `{"error": {"code": "VALIDATION_ERROR", "details": [{"field": "items[0].quantity", "issue": "must be >= 1"}]}}` |
| 500 | Ошибка сервера | `{"error": {"code": "INTERNAL_ERROR"}}` |

**Что проверяет аналитик:**

- все ли сценарии описаны;
- у каждой ошибки есть код;
- в теле достаточно информации для отладки;
- клиент понимает, что делать с каждой ошибкой (retry / показать пользователю / залогировать).
