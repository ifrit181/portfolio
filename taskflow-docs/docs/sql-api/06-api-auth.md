## <a id="1-аутентификация-vs-авторизация">1. Аутентификация vs авторизация</a>

**Аутентификация** — проверка, кто обращается к API. Отвечает на вопрос
«кто ты?».

**Авторизация** — проверка, что этому «кому» разрешено делать. Отвечает на
вопрос «что тебе можно?».

| | Аутентификация | Авторизация |
|---|---|---|
| Вопрос | Кто ты? | Что тебе можно? |
| Что проверяет | Подлинность клиента | Права клиента |
| Пример | Логин + пароль, токен | Роль admin, scope `write:orders` |
| Код ошибки | `401 Unauthorized` | `403 Forbidden` |

**Порядок проверки:** сначала аутентификация, потом авторизация. Если клиент
не аутентифицирован — сервер не проверяет права, сразу возвращает `401`.

**Пример.** Пользователь Иван с ролью `user` вызывает `DELETE /orders/1`.

1. Сервер проверяет токен → Иван существует. ✅ Аутентификация пройдена.
2. Сервер проверяет права → у роли `user` нет права удалять заказы.
3. Возвращает `403 Forbidden`. ✅ Авторизация не пройдена.

📖 Разница между `401` и `403` — в [05-api-rest.md](05-api-rest.md) → раздел 5.

## <a id="2-api-ключи">2. API-ключи</a>

**API-ключ** — уникальная строка, которую клиент передаёт в заголовке для
идентификации. Сервер сверяет ключ с хранилищем и определяет, кому он выдан.

**Пример:**

```http
GET /api/v1/orders
X-API-Key: 5f4dcc3b5aa765d61d8327deb882cf99
```

**Как это работает:**

1. Клиент получает ключ при регистрации в системе.
2. Передаёт ключ в каждом запросе в заголовке `X-API-Key` (или `Authorization`).
3. Сервер проверяет ключ и определяет владельца.

**Плюсы:**

- просто реализовать;
- легко выдать и отозвать;
- не требует логина и пароля в каждом запросе.

**Минусы:**

- ключ легко утекает (попадает в логи, URL, публичные репозитории);
- у ключа обычно нет срока жизни — утёк, значит, действует вечно;
- нет гранулярных прав — либо всё, либо ничего;
- нет стандарта, каждая система использует свой формат заголовка.

**Где встречается:** внутренние сервисы, публичные API для разработчиков
(например, доступ к данным о погоде, курсах валют).

**Что описывает аналитик:**

- имя заголовка (`X-API-Key` или `Authorization`);
- формат ключа (длина, префикс);
- срок действия (если есть);
- как отзывается ключ;
- как ключ передаётся (только HTTPS).

## 3. Basic Auth

**Basic Auth** — передача логина и пароля в заголовке `Authorization`.
Логин и пароль объединяются через `:`, кодируются в **base64** и помещаются
в заголовок.

**Пример:**

```http
Authorization: Basic dXNlcjpwYXNzd29yZA==
```

`dXNlcjpwYXNzd29yZA==` — это `user:password`, закодированное в base64.

**Как это работает:**

1. Клиент формирует строку `login:password`.
2. Кодирует её в base64.
3. Передаёт в заголовке `Authorization: Basic <закодированная строка>`.
4. Сервер декодирует, проверяет логин и пароль.

**Важно:** base64 — это **не шифрование**, а кодирование. Любой, кто
перехватит запрос, легко декодирует логин и пароль.

**Правила использования:**

- только по **HTTPS** — иначе пароль виден в открытом виде;
- не использовать в публичных API;
- применять для простых внутренних сервисов или для отладки.

**Что описывает аналитик:**

- требование HTTPS;
- формат заголовка;
- поведение при неверных данных (`401 Unauthorized`);
- ограничение на количество попыток (защита от брутфорса).

## <a id="4-oauth-2-0">4. OAuth 2.0</a>

**OAuth 2.0** — протокол делегированной авторизации. Позволяет приложению
получить доступ к ресурсам пользователя в другой системе **без передачи
пароля**. Вместо пароля используется токен с ограниченными правами и сроком
жизни.

**Пример.** Пользователь хочет, чтобы приложение «Календарь» читало его
встречи из Google Calendar. Он не передаёт пароль от Google приложению.
Вместо этого Google выдаёт приложению токен с правом только на чтение
календаря.

### <a id="участники">Участники</a>

| Роль | Кто это |
|---|---|
| **Resource Owner** | Пользователь, чьи данные запрашиваются |
| **Client** | Приложение, которое запрашивает доступ |
| **Authorization Server** | Сервер, выдающий токены |
| **Resource Server** | API с защищёнными данными |

### <a id="основные-flow">Основные flow</a>

**Authorization Code** — для серверных приложений, где есть бэкенд.

1. Клиент перенаправляет пользователя на Authorization Server.
2. Пользователь логинится и подтверждает доступ.
3. Authorization Server возвращает клиенту **код авторизации**.
4. Клиент обменивает код на **access_token** через прямой запрос.
5. Клиент использует `access_token` для доступа к API.

**Почему через код, а не сразу токен.** Код передаётся через браузер
(публичный канал), а токен — через прямой запрос сервер-сервер
(защищённый канал). Так токен не попадает в логи браузера.

**Client Credentials** — для сервис-сервис, когда нет пользователя.

```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=abc
&client_secret=xyz
```

Сервер проверяет `client_id` и `client_secret` и выдаёт `access_token`.
Этот flow используется, когда одна система обращается к другой без участия
пользователя.

**Refresh Token** — обновление `access_token` без повторного логина.
Клиент передаёт `refresh_token` и получает новый `access_token`.

### <a id="токены">Токены</a>

| Токен | Назначение | Срок жизни |
|---|---|---|
| `access_token` | Доступ к API | Короткий (минуты, часы) |
| `refresh_token` | Обновление access-токена | Долгий (дни, месяцы) |

**Почему два токена.** Короткий `access_token` ограничивает ущерб при утечке:
даже если он украден, злоумышленник получит доступ на минуты. `refresh_token`
хранится на сервере клиента и не передаётся по сети так часто.

**Что описывает аналитик:**

- какой flow используется;
- где хранится `refresh_token` (только на сервере, не в браузере);
- срок жизни токенов;
- scope'ы — какие права запрашиваются;
- поведение при истечении `refresh_token` — повторный логин.

## 5. JWT (JSON Web Token)

**JWT** — формат токена, состоящий из трёх частей, разделённых точкой:
`header.payload.signature`.

**Структура:**

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6ItCY0LLQsNC9In0.abc123signature
```

| Часть | Что содержит |
|---|---|
| Header | Алгоритм подписи (`HS256`, `RS256`) и тип токена |
| Payload | Данные: идентификатор пользователя, роль, срок жизни |
| Signature | Подпись, по которой сервер проверяет, что токен не изменён |

**Пример payload:**

```json
{
  "sub": "1234567890",
  "name": "Иван Иванов",
  "role": "admin",
  "iat": 1737000000,
  "exp": 1737003600
}
```

| Поле | Значение |
|---|---|
| `sub` | Идентификатор пользователя (subject) |
| `iat` | Когда выдан (issued at) |
| `exp` | Когда истекает (expiration) |
| `role` | Роль пользователя — для авторизации |

**Передача:**

```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

**Ключевое свойство.** JWT **подписан**, но **не зашифрован**. Любой может
декодировать payload и прочитать данные. Подпись гарантирует только то, что
токен не изменён. Поэтому в payload нельзя хранить секреты: пароли,
номера карт, персональные данные.

**Что проверяет сервер:**

1. Подпись валидна — токен не подделан.
2. `exp` не истёк — токен актуален.
3. `sub` указывает на существующего пользователя.
4. `role` или `scope` даёт право на операцию.

**Что описывает аналитик:**

- алгоритм подписи (`HS256` — симметричный, `RS256` — асимметричный);
- обязательные поля в payload (`sub`, `exp`, `iat`, `role`);
- срок жизни (`exp`);
- что делать при истёкшем токене (`401` с кодом `TOKEN_EXPIRED`);
- запрет на хранение секретов в payload.

## <a id="6-что-описывать-аналитику">6. Что описывать аналитику</a>

### <a id="в-спецификации-api">В спецификации API</a>

| Пункт | Пример |
|---|---|
| Тип аутентификации | Bearer JWT |
| Где передаётся | Заголовок `Authorization` |
| Срок жизни токена | 1 час |
| Как обновляется | Через `refresh_token` |
| Скоупы / роли | `read:orders`, `write:orders` |
| Поведение при `401` | Клиент обновляет токен и повторяет запрос |
| Поведение при `403` | Показать пользователю «нет доступа» |

### <a id="в-сценариях">В сценариях</a>

**Сценарий 1: успешный запрос**

1. Клиент получает `access_token` через OAuth.
2. Вызывает API с заголовком `Authorization: Bearer <token>`.
3. Получает `200 OK`.

**Сценарий 2: токен истёк**

1. API отвечает `401` с кодом `TOKEN_EXPIRED`.
2. Клиент вызывает `/oauth/token` с `refresh_token`.
3. Получает новый `access_token`.
4. Повторяет исходный запрос.

**Сценарий 3: нет прав**

1. API отвечает `403 Forbidden`.
2. Клиент показывает пользователю сообщение «нет доступа к операции».

**Сценарий 4: `refresh_token` истёк**

1. API отвечает `401` с кодом `REFRESH_TOKEN_EXPIRED`.
2. Клиент перенаправляет пользователя на страницу логина.
3. Пользователь логинится заново, получает новую пару токенов.

📖 Сценарии ошибок в интеграциях — в [17-api-idempotency.md](17-api-idempotency.md) → раздел 5.

## <a id="7-практика">7. Практика</a>

### <a id="задача-1">Задача 1</a>
Опишите в спецификации схему авторизации для endpoint'а создания заказа.

```yaml
security:
  - bearerAuth: []
securitySchemes:
  bearerAuth:
    type: http
    scheme: bearer
    bearerFormat: JWT
```

**Требования:**

- заголовок `Authorization: Bearer <access_token>`;
- scope `write:orders`;
- при `401` — обновить токен и повторить;
- при `403` — вернуть ошибку пользователю.

### <a id="задача-2">Задача 2</a>
Опишите матрицу ролей для API.

| Endpoint | user | manager | admin |
|---|---|---|---|
| `GET /orders` | Свои | Все | Все |
| `POST /orders` | ✅ | ✅ | ✅ |
| `DELETE /orders/{id}` | ❌ | ✅ | ✅ |
| `GET /users` | ❌ | Своя команда | Все |

**Что важно в матрице:**

- для каждой роли явно указано, что разрешено;
- для строк с ограничением по объекту («Свои», «Своя команда») указано,
  как сервер проверяет владение;
- запрет обозначен явно (`❌`), чтобы не было двусмысленности.

📖 Проверка владения объектом — в [24-api-security.md](24-api-security.md) → раздел 2.

### <a id="задача-3">Задача 3</a>
Опишите сценарий обновления истёкшего токена.

| Шаг | Действие клиента | Ответ сервера |
|---|---|---|
| 1 | `GET /orders` с `access_token` | `401` `TOKEN_EXPIRED` |
| 2 | `POST /oauth/token` с `refresh_token` | `200` + новый `access_token` |
| 3 | `GET /orders` с новым `access_token` | `200` + данные |
| 4 | Если `refresh_token` истёк на шаге 2 | `401` `REFRESH_TOKEN_EXPIRED` |
| 5 | Перенаправление на логин | — |
