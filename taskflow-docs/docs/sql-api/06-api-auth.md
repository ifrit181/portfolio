## 1. Аутентификация vs авторизация

| | Аутентификация | Авторизация |
|---|---|---|
| Вопрос | Кто ты? | Что тебе можно? |
| Пример | Логин + пароль | Роль admin |
| Код ошибки | 401 Unauthorized | 403 Forbidden |

## 2. API-ключи

Простейший способ: клиент передаёт ключ в заголовке.

```http
GET /api/v1/orders
X-API-Key: 5f4dcc3b5aa765d61d8327deb882cf99
```

**Плюсы:** просто.
**Минусы:** ключ легко утекает; нет срока жизни; нет гранулярных прав.

**Где встречается:** внутренние сервисы, публичные API для разработчиков.

---

## 3. Basic Auth

Логин и пароль в base64 в заголовке.

```http
Authorization: Basic dXNlcjpwYXNzd29yZA==
```

⚠️ **Только по HTTPS.** В открытом виде — небезопасно.

## 4. OAuth 2.0

Протокол делегированной авторизации. Позволяет приложению получить доступ к ресурсам пользователя без передачи пароля.

### Участники

| Роль | Кто это |
|---|---|
| Resource Owner | Пользователь |
| Client | Приложение |
| Authorization Server | Сервер авторизации |
| Resource Server | API с данными |

### Основные flow

**Authorization Code** — для серверных приложений:
1. Клиент → редирект на Authorization Server.
2. Пользователь логинится.
3. Authorization Server → код.
4. Клиент → обменивает код на токен.
5. Клиент → использует `access_token`.

**Client Credentials** — для сервис-сервис:
```http
POST /oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials
&client_id=abc
&client_secret=xyz
```

**Refresh Token** — обновление access-токена без повторного логина.

### Токены

| Токен | Назначение | Срок жизни |
|---|---|---|
| `access_token` | Доступ к API | Короткий (мин/часы) |
| `refresh_token` | Обновление access | Долгий (дни/месяцы) |

## 5. JWT (JSON Web Token)

Токен из трёх частей через точку: `header.payload.signature`.

**Пример payload:**
```json
{
  "sub": "1234567890",
  "name": "Иван Иванов",
  "role": "admin",
  "iat": 1737000000,
  "exp": 1737003600
}
```

| Поле | Значение |
|---|---|
| `sub` | Идентификатор пользователя |
| `iat` | Выдан (issued at) |
| `exp` | Истекает (expiration) |
| `role` | Роль (для авторизации) |

**Передача:**
```http
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

⚠️ JWT **подписан**, но не зашифрован — не хранить в нём секреты.

## 6. Что описывать аналитику

### В спецификации API

| Пункт | Пример |
|---|---|
| Тип аутентификации | Bearer JWT |
| Где передаётся | `Authorization` header |
| Срок жизни токена | 1 час |
| Как обновляется | Через `refresh_token` |
| Скоупы / роли | `read:orders`, `write:orders` |
| Поведение при 401 | Клиент обновляет токен и повторяет |
| Поведение при 403 | Показать «нет доступа» |

### В сценариях

**Сценарий 1: успешный запрос**
1. Клиент получает `access_token` через OAuth.
2. Вызывает API с заголовком `Authorization: Bearer <token>`.
3. Получает 200.

**Сценарий 2: токен истёк**
1. API отвечает 401 с `code: TOKEN_EXPIRED`.
2. Клиент вызывает `/oauth/token` с `refresh_token`.
3. Получает новый `access_token`.
4. Повторяет исходный запрос.

**Сценарий 3: нет прав**
1. API отвечает 403.
2. Клиент показывает ошибку пользователю.

## 7. Практика

### Задача 1
Опишите в спецификации схему авторизации для endpoint'а создания заказа.

```yaml
security:
  - bearerAuth: []
securitySchemes:
  bearerAuth:
    type: http
    scheme: bearer
    bearerFormat: JWT
```

**Требования:**
- заголовок `Authorization: Bearer <access_token>`;
- scope `write:orders`;
- при 401 — обновить токен и повторить;
- при 403 — вернуть ошибку пользователю.

### Задача 2
Опишите матрицу ролей для API.

| Endpoint | user | manager | admin |
|---|---|---|---|
| GET /orders | Свои | Все | Все |
| POST /orders | ✅ | ✅ | ✅ |
| DELETE /orders/{id} | ❌ | ✅ | ✅ |
| GET /users | ❌ | Своя команда | Все |
