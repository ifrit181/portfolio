## <a id="1-как-пользоваться-памяткой">1. Как пользоваться памяткой</a>

Памятка работает в двух режимах:

**Режим «подготовка к собеседованию».** Проходите блоки по порядку.
На каждый вопрос отвечайте вслух, не подглядывая. Если ответ неполный —
переходите по ссылке на файл курса и перечитывайте раздел.

**Режим «повторение курса».** Используйте раздел 12 как карту: он
показывает, какие темы курса закрывают какие вопросы собеседования.

**Соглашение.** В каждом блоке:

- таблица «Вопрос → Что отвечать» — краткие ответы;
- ссылки `📖` — куда вернуться за подробностями;
- пометка 🎯 — вопрос, который задают чаще всего.

## <a id="2-требования-и-работа-с-бизнесом">2. Требования и работа с бизнесом</a>

📖 Подробнее: [09-sql-api-workflow.md](09-sql-api-workflow.md)

| Вопрос | Что отвечать |
|---|---|
| 🎯 Как выявляете требования? | Интервью, воркшопы, анализ текущих процессов, изучение БД и логов, анализ аналогов |
| 🎯 Чем User Story отличается от Use Case? | US — «как \<роль\>, я хочу \<действие\>, чтобы \<цель\>». UC — пошаговый сценарий с альтернативами |
| Что такое acceptance criteria? | Условия, при которых задача считается выполненной |
| Как приоритизируете? | MoSCoW, RICE, WSJF. Выбор зависит от проекта |
| 🎯 Что делать, если бизнес и разработка не сходятся? | Собрать факты, показать ограничения обеим сторонам, найти компромисс, зафиксировать решение |
| Что такое NFR? | Нефункциональные требования: производительность, безопасность, доступность, масштабируемость |
| Как валидируете требования? | Проверяю на полноту, непротиворечивость, реализуемость; согласую с бизнесом и разработкой |
| Что делать, если требования меняются в середине спринта? | Оценить влияние, согласовать приоритет, зафиксировать изменение, обновить документацию |

**Что важно упомянуть:** non-functional requirements спрашивают почти
всегда. Готовьте пример: «SLA по времени синхронизации — 60 секунд».

| Тема | Что должны знать |
|---|---|

| Оконные функции | `ROW_NUMBER`, `LAG`, `SUM OVER` |
| CTE | `WITH ... AS (...)` |

| Вопрос | Что отвечать |
|---|---|
| 🎯 Чем `PUT` отличается от `PATCH`? | `PUT` — полная замена, `PATCH` — частичная |
| 🎯 Что такое идемпотентность? | Повторный вызов даёт тот же результат |

| Как версионировать API? | В URL (`/api/v1/`) или заголовке |

## <a id="8-soft-skills-что-проверяют">8. Soft skills — что проверяют</a>

📖 Подробнее: [09-sql-api-workflow.md](09-sql-api-workflow.md) → [раздел 2](09-sql-api-workflow.md#2-типовой-workflow-аналитика)

| Что проверяют | Что показать в ответе |
|---|---|
| Переговоры с бизнесом | Пример, когда договорились о компромиссе |
| Реакция на изменения | Как перестраивали план, что фиксировали |
| Конфликт «бизнес vs разработка» | Как собрали факты и нашли решение |
| Приоритизация | Как выбирали между срочным и важным |
| Объяснение сложного | Пример, когда объяснили техническую тему бизнесу |

**Формула ответа на поведенческий вопрос — STAR:**

- **S**ituation — ситуация.
- **T**ask — задача.
- **A**ction — что сделали.
- **R**esult — результат.

**Пример.** «На прошлом проекте (S) нужно было за 2 недели
синхронизировать заказы между магазином и 1С (T). Я описал контракт API,
маппинг полей и сценарии ошибок, согласовал с обеими командами (A).
В итоге синхронизация запустилась в срок, дубли не создавались (R)».

## <a id="11-чек-лист-за-день-до-собеседования">11. Чек-лист за день до собеседования</a>

- [ ] Повторить SQL: `JOIN`, `GROUP BY`, оконные функции.
- [ ] Написать 2–3 запроса без подсказок.
- [ ] Повторить API: методы, статус-коды, идемпотентность.
- [ ] Повторить разницу `401` / `403`, `PUT` / `PATCH`.
- [ ] Вспомнить 2–3 кейса из практики в формате STAR.
- [ ] Подготовить вопросы к интервьюеру.
- [ ] Проверить, что можете объяснить **любой** пункт из своего резюме.
- [ ] Прочитать памятку ещё раз — разделы 2, 4, 5.
- [ ] Выспаться.
