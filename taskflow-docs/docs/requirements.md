# Требования к оформлению документации

Единый стандарт оформления технической документации. Используется как чек-лист
при приёмке документов и как ТЗ при создании новых шаблонов.

---

## 1. Общие принципы

| № | Требование | Обоснование |
| --- | --- | --- |
| 1.1 | Единый шаблон для всех документов одного типа | Обеспечивает узнаваемость и снижает трудозатраты |
| 1.2 | Оформление отделено от контента | Контент в Markdown, стили — в шаблоне |
| 1.3 | Шаблон версионируется в Git | Изменения оформления отслеживаются |
| 1.4 | Смена шаблона меняет оформление без правок контента | Ключевой принцип Docs as Code |
| 1.5 | Документ собирается автоматически из источника | Ручная вёрстка исключена |

## 3. Титульный лист

- [x] Название продукта или раздела
- [x] Тип документа (руководство пользователя, руководство администратора, инструкция)
- [x] Версия документа — берётся из Release notes автоматически
- [x] Автор или владелец документа
- [x] Дата выпуска
- [ ] Логотип или фирменный визуальный элемент (опционально)
- [x] Рамка по периметру — для официальных документов
- [x] Отдельная секция с собственным колонтитулом (или без него)

## 4. Колонтитулы

### 4.1. Верхний колонтитул

| № | Требование |
| --- | --- |
| 4.1.1 | Название документа слева |
| 4.1.2 | Тип документа (если отличается от названия) |
| 4.1.3 | Версия документа — синхронизирована с Release notes |
| 4.1.4 | Номер страницы — «Страница X из Y» |
| 4.1.5 | Тонкая разделительная линия между колонтитулом и текстом |
| 4.1.6 | Шрифт мельче основного (9 pt), приглушённый цвет |

### 4.2. Нижний колонтитул

| № | Требование |
| --- | --- |
| 4.2.1 | Копирайт или пометка о правах |
| 4.2.2 | Единый формат на всех страницах |
| 4.2.3 | Отсутствует на титульном листе (особая первая страница) |

## 5. Версионность и Release notes

| № | Требование |
| --- | --- |
| 5.1 | Все версии документа ведутся в одном источнике (YAML, таблица, Release notes) |
| 5.2 | Текущая версия в шапке = последняя запись в списке версий |
| 5.3 | Таблица «Изменения в документе» формируется автоматически из того же источника |
| 5.4 | Колонки таблицы: Версия, Дата, Автор, Описание |
| 5.5 | Формат версии единый: `X.Y` или `X.Y.Z` |
| 5.6 | Формат даты единый: `ДД.ММ.ГГГГ` |
| 5.7 | Добавление новой версии в источник обновляет и шапку, и таблицу |

## 9. Врезки (admonition)

| № | Тип | Фон | Левая полоса | Иконка |
| --- | --- | --- | --- | --- |
| 9.1 | Примечание | `F2EEE6` | `A67C52` | :material-information-outline: |
| 9.2 | Предупреждение | `FBF3E0` | `C89848` | :material-alert-outline: |
| 9.3 | Внимание | `F5E4DE` | `9C3A28` | :material-alert-octagon-outline: |
| 9.4 | Совет | `EEF2EC` | `7A8B6F` | :material-lightbulb-on-outline: |

**Общие требования:**

- единый формат по всему документу;
- заголовок врезки — полужирный;
- содержимое — без абзацного отступа;
- врезка не разрывается между страницами;
- врезка не попадает в TOC.

## 10. Таблицы

| № | Требование |
| --- | --- |
| 10.1 | Шапка — заливка, полужирный текст |
| 10.2 | Границы — тонкие, единого цвета |
| 10.3 | Чередование строк (опционально) |
| 10.4 | Отступы в ячейках — 80–120 twips |
| 10.5 | Шапка повторяется при переносе на новую страницу |
| 10.6 | Ширина колонок фиксирована и одинакова для однотипных таблиц |
| 10.7 | Выравнивание в ячейках: текст — влево, числа — вправо, заголовки — по центру |
| 10.8 | Подпись таблицы — над таблицей, формат «Таблица N — Название» |
| 10.9 | Нумерация таблиц — сквозная или по разделам |

## 18. Чек-лист перед выпуском

- [ ] Титульный лист заполнен корректно
- [ ] Версия совпадает с последней записью в Release notes
- [ ] TOC обновлён, все разделы на месте
- [ ] Нет пустых страниц
- [ ] Нет кракозябр и артефактов
- [ ] Нумерация разделов, рисунков, таблиц сквозная и корректная
- [ ] Все ссылки работают
- [ ] Врезки оформлены единообразно
- [ ] Колонтитулы на всех страницах, кроме титула
- [ ] Номера страниц корректны
- [ ] Документ открывается в Word, PDF, Google Docs без ошибок
- [ ] PDF не имеет артефактов конвертации
- [ ] Терминология единая
- [ ] Линтер пройден без ошибок

---

## Как использовать этот список

1. **Как чек-лист при приёмке** — пройти по пунктам перед выпуском документа.
2. **Как ТЗ для шаблона** — при создании нового шаблона.
3. **Как раздел портфолио** — показать системный подход к документации.
4. **Как аргумент на интервью** — «У меня есть список требований к оформлению, по которому я проверяю каждый документ».

---

## Что можно добавить

- **Требования к локализации** — если документ переводится.
- **Требования к доступности** — контраст, размер шрифта, альтернативные тексты.
- **Требования к версиям для печати** — поля, отсутствие фона, ч/б.
- **Требования к метаданным** — автор, дата, ключевые слова в свойствах `.docx`.
